# FireTV — Native ↔ JavaScript Architecture

How the Android/Cordova native layer and the hosted web app communicate in the
Vizbee Sample App on Amazon FireTV.

---

## If you are new to FireTV development

### What is a FireTV app?

- Amazon FireTV runs **Fire OS**, which is Amazon's fork of Android. A FireTV app
  is an Android app (`.apk` file) — the same technology you use to build Android
  phone apps.
- The app is written in **Java** (or Kotlin). It defines an **Activity** — the
  full-screen "window" that runs when the user launches your app from the FireTV
  home screen.
- Amazon distributes apps through the **Amazon Appstore**. For development you
  sideload the APK directly over ADB (USB or network).

### What is Cordova?

- **Apache Cordova** is a framework that lets you build mobile/TV apps using web
  technologies (HTML, CSS, JavaScript) instead of writing pure native code.
- Cordova generates a standard Android project for you. At its core it is an
  Android Activity that contains a **WebView** — essentially a full-screen
  embedded browser.
- Your web app runs inside that WebView. Cordova provides a plugin system so JS
  code can call native device APIs (camera, storage, etc.).
- In this project, Cordova is used purely as a **packaging tool**: it produces
  the APK, manages the Android project scaffolding, and lets us inject a custom
  native bridge through a plugin.

### What Java code is in this app?

There are two Java files, both inside `platforms/firetv/vizbee-bridge/src/android/`:

- **`VizbeeBridgePlugin.java`** — a Cordova plugin. Cordova calls its
  `initialize()` method automatically when the app starts. All it does is
  register `NativeBridge` with the WebView so JavaScript can reach it.
- **`NativeBridge.java`** — the object that becomes `window.VizbeeBridge` in
  JavaScript. Every `public` method annotated with `@JavascriptInterface` is
  callable from JS. Currently it exposes `getDeviceInfo()`, `exit()`, and
  placeholder stubs for future Vizbee SDK calls.

There is also a **`MainActivity.java`** (auto-generated by Cordova, then patched
by a build script hook). Normally it does nothing special — the hook adds an
`onBackPressed()` override so the Android BACK button is forwarded to JavaScript
instead of closing the app immediately.

### How does JavaScript run on FireTV?

- The Cordova APK opens a **WebView** — think of it as Chrome embedded inside the
  app.
- The WebView loads a small local HTML file (`www/index.html`) that immediately
  redirects to the hosted sample webapp URL (on CloudFront).
- From that point on, everything you see is rendered by the **hosted web app**
  (HTML/CSS/TypeScript), exactly like opening a webpage in a browser.
- The web app **does not know it is inside an APK** — except that
  `window.VizbeeBridge` exists, which only exists inside our Cordova WebView.
  `FireTVAdapter.ts` checks for this object to detect the FireTV platform.

### How does the BACK button work?

- On a phone, pressing BACK navigates to the previous screen.
- On a TV remote, the BACK button press reaches Android's `Activity.onBackPressed()`
  — NOT a JavaScript key event.
- Without special handling, pressing BACK would close the entire app with no
  confirmation dialog.
- Our fix: a build script patches `MainActivity.java` to intercept the BACK press
  and call `WebView.evaluateJavascript()`, which runs JavaScript code that
  dispatches a synthetic keyboard event (`keyCode 4`) into the web page.
- The web app's `RemoteKeyService` maps `keyCode 4 → 'BACK'`, so the existing
  exit-confirm dialog on the Home page and back-navigation in the Player work
  without any changes.

### Key terms at a glance

| Term | What it means |
|------|--------------|
| APK | Android application package — the installable file |
| Activity | The Android "screen" that hosts the WebView |
| WebView | An embedded browser widget inside an Android app |
| Cordova plugin | Java code that extends the WebView with native APIs |
| `@JavascriptInterface` | Java annotation that exposes a method to JavaScript |
| `addJavascriptInterface` | Android API that injects a Java object as a JS global |
| `evaluateJavascript` | Android API that runs a JS string inside the WebView |
| ADB | Android Debug Bridge — the command-line tool to install/debug APKs |
| Fire OS | Amazon's Android fork that runs on FireTV devices |

## Bridge mechanism: `addJavascriptInterface`

Standard Cordova plugins use `cordova.exec()` which requires `cordova.js` to be
loaded in the page. That doesn't work for an **external URL** (the hosted webapp
doesn't load `cordova.js`).

Instead, `VizbeeBridgePlugin.java` calls:

```java
// VizbeeBridgePlugin.java — initialize(), called once at WebView creation
WebView nativeWebView = (WebView) webView.getEngine().getView();
nativeWebView.addJavascriptInterface(new NativeBridge(cordova), "VizbeeBridge");
```

`addJavascriptInterface(object, name)` injects the Java object into the WebView's
JavaScript environment as `window.VizbeeBridge`. Key properties:

| Property | Detail |
|---|---|
| **Scope** | Injected at the WebView instance level — not per-page or per-origin |
| **Persistence** | Survives `window.location.replace()` and all subsequent navigations |
| **Thread** | Java methods run on a background thread, not the UI thread |
| **Direction** | JS → Native only (see "Native → JS" section below for the reverse) |
| **Security** | Exposed to ALL content in the WebView — only navigate to trusted URLs |

## Back button handling

On Android the BACK button is intercepted natively by `CordovaActivity.onBackPressed()`
before any JavaScript keydown event fires. Without intervention, pressing BACK
exits the Activity immediately — the JS exit-confirm dialog on the Home page never
shows.

**Fix: Cordova hook** (`hooks/after_platform_add/override-back-button.js`)

The hook patches the generated `MainActivity.java` after `cordova platform add android`:

```java
// Patched MainActivity.java (generated + patched by the hook)
@Override
public void onBackPressed() {
    // Dispatch keydown(keyCode=4) to JS instead of closing the Activity.
    // FIRETV_KEYS maps keyCode 4 → 'BACK' in keymaps.ts, so the existing
    // exit-confirm dialog on Home and back-navigation in Player/Settings work.
    if (appView != null) {
        ((android.webkit.WebView) appView.getEngine().getView())
            .evaluateJavascript("...", null);
    }
    // super.onBackPressed() intentionally NOT called — Activity.finish() is
    // triggered only when the user confirms exit via window.VizbeeBridge.exit().
}
```

**Web-side keymap** (`src/core/input/keymaps.ts` — `FIRETV_KEYS`):

```ts
const FIRETV_KEYS = {
  ...COMMON_NAVIGATION,   // arrows + Enter
  4:   'BACK',            // Android KEYCODE_BACK (injected synthetically)
  415: 'PLAY',
  19:  'PAUSE',
  179: 'PLAY_PAUSE',
  413: 'STOP',
  417: 'FAST_FORWARD',
  412: 'REWIND',
};
```

The hook runs automatically via `cordova platform add android` AND is re-applied on
every `npm run apk:firetv` (idempotent — skips if `onBackPressed` is already present).

```
  ▼

  │  All plugins confirmed ready
  │
  ▼

  │  WebView navigates to the hosted webapp
  │  window.VizbeeBridge persists across this navigation
  │
  ▼

  │  (bridge detected on window, or waits for deviceready/DOMContentLoaded)
  │
  ▼

```

## JS → Native calls

```ts
// FireTVAdapter.ts
const raw = window.VizbeeBridge?.getDeviceInfo();  // → JSON string
const info = JSON.parse(raw);
// { platform:"firetv", model:"AFTN", manufacturer:"Amazon",
//   osVersion:"9", sdkInt:28 }

window.VizbeeBridge?.exit();  // → Activity.finish()
```

Java side — `@JavascriptInterface` is **required** (API 17+ security):

```java
@JavascriptInterface
public String getDeviceInfo() { ... }

@JavascriptInterface
public void exit() { cordova.getActivity().finish(); }
```

## Native → JS calls

`addJavascriptInterface` is one-directional. To push data from native:

```java
webView.getEngine().evaluateJavascript(
    "window.dispatchEvent(new CustomEvent('vizbee:event', { detail: " + json + " }))",
    null
);
```

Web side:
```ts
window.addEventListener('vizbee:event', (e: CustomEvent) => { ... });
```

The back-button patch already uses this pattern (`keydown` dispatch). Vizbee SDK
cast-state callbacks will follow the same path.

## Known build gotchas

### appcompat `Invalid <color>` error
`cordova-android@14` pulls in `appcompat` which has a known bug with Android
Build Tools 35 — the AAPT2 resource compiler rejects `?attr/` references inside
`<color>` elements. `build-firetv.sh` auto-creates
`platforms/android/app/build-extras.gradle` to set `buildToolsVersion '33.0.2'`
(or whichever version is installed).

### `BackgroundColor` preference
Do **not** add `<preference name="BackgroundColor" value="0xff...">` to
`config.xml`. Cordova writes the `0x`-prefixed hex to an Android resource file
where it is invalid, causing the same `Invalid <color>` build failure.
Dark background is handled instead by `<html style="background:#07090c">` in
`index.html` (covers the page before CSS loads) and `background: #000` in
`www/index.html` (covers the Cordova launcher screen).

## Adding a new bridge method

1. **Java** — add `@JavascriptInterface` method to `NativeBridge.java`
2. **TypeScript** — add signature to `VizbeeBridgeInterface` in `FireTVAdapter.ts`
3. **Call site** — `window.VizbeeBridge?.newMethod()`
4. **Rebuild** — `rm -rf platforms/firetv/platforms platforms/firetv/plugins && npm run apk:firetv`

## Vizbee SDK integration (future)

```
NativeBridge.java
  │  Vizbee Android SDK initialised in VizbeeBridgePlugin.initialize()
  │
  ├── getVizbeeDeviceId()     → SDK device ID → FireTVAdapter.ts
  ├── getHomeSSOStatus()      → HomeSSO sign-in state → HomeSSOService.ts
  └── evaluateJavascript()    → push cast events to web layer
```

Settings flags (`sdkEnv`, `playerElement`, etc.) are visible in the app UI and
persist to `localStorage` — they have no runtime effect until the SDK is wired.
